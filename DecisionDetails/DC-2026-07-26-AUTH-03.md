# DC-2026-07-26-AUTH-03 — Protected routes can hand off signed human identity

## Context

GlobalFinance's `gf2.vr.ae` test route was already protected by DevOps Console Google authentication and an exact `route:gf2` grant. GlobalFinance independently required a Keycloak browser session, so a Console-authorized request reached `/api/auth/session` without that inner session and returned 401; the Console correctly projected the protected-upstream credential failure as its branded 502 page. The owner requires the test server to expose full controls after the one Console login, with mutations attributable to the signed-in human.

The existing fixed upstream bearer credential cannot meet that requirement: it authenticates the Console route service, not the individual human. The earlier plain trusted-header alternative remains rejected by `DC-2026-07-16-AUTH-01` because any process that can reach the loopback listener could forge it.

## Selected boundary

DevOps Console owns a private Ed25519 key in its mode-0600 state and publishes only its public JWK at `/.well-known/devops-console-identity.jwks`. After the normal Console session and exact route grant succeed, it signs a JWT with a 15-second maximum lifetime and exact `iss`, `aud`, `sub`, `resource`, `method`, `iat`, `exp`, and UUID-v4 `jti` claims. The proxy deletes any caller-supplied `X-DevOps-Console-Assertion` before route policy is evaluated and injects its generated value only for an authorized protected request, including WebSocket upgrades.

GlobalFinance enables this mode only under its development profile. It verifies the Ed25519 signature and exact Console key shape, issuer, public host, `route:gf2` grant, HTTP method, lifetime, normalized email, and UUID. It atomically consumes a SHA-256-derived one-time key in its existing auth Valkey, failing closed when either JWKS or replay storage is unavailable. Only then does it map the human to the test server's researcher, steward, and operator groups. Unsafe methods additionally require the normal browser CSRF header, and audit writes use `devops-console:<email>`.

Production and stage continue to reject this access mode. Console login/logout routes stay disabled on this test surface because the Console owns that browser session.

## Verification

- Console unit tests prove private-key permissions and stable key identity, public JWKS redaction, exact claims and Ed25519 signature, invalid-input rejection, caller-header stripping/replacement for HTTP and WebSocket, and public-route stripping.
- The full Console TLS-stack test fetches the anonymous public JWKS, sends an authenticated protected request, verifies its signature and exact email/host/route/method claims, and confirms the 15-second lifetime.
- GlobalFinance middleware tests prove all five permissions, the real Console email audit actor, successful CSRF-bound mutation, anonymous rejection, missing-CSRF rejection, wrong-key/wrong-method rejection, and one-time replay rejection.
- GlobalFinance runtime/deploy tests prove explicit dev configuration and production rejection; UI tests prove the no-expiry Console session contract and retain CSRF on all unsafe same-origin requests.

Runtime publication remains a separate coordinated deployment step. Source verification does not claim that the currently running Console process or GlobalFinance containers have reloaded these files.
