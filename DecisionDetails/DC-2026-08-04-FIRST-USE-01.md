# DC-2026-08-04-FIRST-USE-01 — First-use repositories adopt themselves on the first bounded runtime mutation

## Decision evidence

- `/home/holyglory/DesignDocEngine/prototype` is a valid newly initialized Git repository with no commit or remote and only untracked product source. Its parent is not a Git repository.
- The installed client profile did not contain that root. `devcoordinator capabilities` therefore rejected it locally as “broker unavailable” before opening a broker connection, even though the broker was healthy and the call journal correctly contained no matching RPC.
- The coding sandbox cannot bind the Vite listener itself. The host Coordinator is the intended runtime owner, but system authority rejected both an unenrolled repository and every target-less `runtime run`; administrator enrollment alone would still leave the application unable to start.
- `security-assumptions.md` confirms one trusted developer across the server's Unix accounts. Repository enrollment is attribution and lifecycle bookkeeping on this host, not authentication between hostile tenants. Path containment, exact identity, operation idempotency, TTL, cleanup, public authorization and credential boundaries remain required.

## Consequences

- Capability and target discovery are non-mutating. A valid root absent from the installed profile is reported as `unenrolled`, with the supported first-use action advertised; it is never mislabeled as a broker outage.
- The first start-like bounded development-service request atomically and idempotently adopts a never-before-seen Git root into broker authority. Existing disabled, retired, missing or identity-conflicting rows are not revived implicitly.
- The temporary service accepts a structured argv vector, repository-relative working directory, exact requested port, bounded non-secret literal environment, positive TTL and explicit cleanup policy. It never accepts a shell string, host mount, secret, arbitrary user switch or fallback port.
- The broker launches the service as the attributed local developer account in the project runtime boundary, persists the definition/session before host launch, returns durable operation/resource handles, retains bounded logs and owns expiry/caller-loss cleanup.
- The installed profile remains a protected bootstrap hint rather than a closed repository catalog. A pure broker-backed repository lookup lets every fresh client resolve an earlier adoption without rewriting installed files or enabling local split-authority fallback.
- Console/API paths do not silently adopt a caller-supplied filesystem path. This first-use journey belongs to the local peer-attributed intent client.

## Verification

- The software-owned delivery cycle creates a zero-commit repository containing only untracked source while the installed profile is stale, proves discovery does not mutate, starts a real strict-port HTTP server through Coordinator, fetches it, verifies repository attribution and then verifies TTL cleanup releases the exact port.
- Focused contracts cover concurrent adoption, lost-reply replay, multiple trusted local caller accounts, linked worktrees, invalid/non-Git roots, path escapes, disabled/tombstoned rows, exact-port collisions, broker unavailability, malformed argv/environment, caller termination, operation-journal correlation and normal plus optimized Python.
