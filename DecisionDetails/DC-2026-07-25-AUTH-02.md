# DC-2026-07-25-AUTH-02 — Rejected private credentials render an operational page

## Supporting record

The authenticated PRTZN route rendered
`{"error":{"code":"UNAUTHORIZED","message":"A valid operator token is required"}}`
as the complete browser page. Production comparison proved that Console's
private `prtzn` Bearer credential no longer matched the independently rotated
control-VM token. The browser session and route grant were valid; another
Google sign-in could not repair this server-held credential drift.

The proxy now handles HTTP 401 from a Google-protected upstream after route
authorization as a configuration failure. It drains and discards the upstream
body, suppresses authentication response headers, and renders the existing
branded HTML error surface with HTTP 502. Public routes retain ordinary
end-to-end HTTP authentication. Missing Console identity remains a 302 for
browser GET/HEAD requests to `/auth/login?rt=<exact requested URL>`.

A focused regression failed before implementation because the protected route
returned 401, then passed with the HTML boundary. Full Console tests passed
243/243, including the TLS full-stack assertion for the exact anonymous return
target and wrong-credential non-disclosure. The production credential was
streamed from the control host into the owner-only Console CLI without entering
argv or output, and the independent PRTZN verifier now passes.

During rollout, a rollback directory inherited mode `0770`; the existing
Console production preflight correctly refused it. The directory was corrected
to `0700` and the state file to `0600`. A second startup gate then exposed an
oversized target-specific Coordinator response; inventory projection was
bounded to the exact target, non-server observations were excluded, and the
real response fell to 14,185 bytes before Console became healthy. The
target-specific self-test now enforces both scope and the 8 MiB ceiling.
