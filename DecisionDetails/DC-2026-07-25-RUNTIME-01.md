# DC-2026-07-25-RUNTIME-01 — Python owns repository-family runtime coordination

## Durable decision

One typed Python request/report boundary owns status, start, stop, restart,
replace, bounded run, and removal for supported services, Docker resources,
local database stacks, and short-lived containers. Ordinary existing-target
actions use schema-derived flags; structured definitions and run commands use a
request file but enter the same validator.

Every request carries the agent, canonical original worktree, explicit linked
temporary worktree or null, immutable resource identity, purpose, TTL, and
KillAfterRun policy. One canonical worktree is one project. Linked temporary
worktrees remain distinct children of their original repository. Ports are
durable assignments, not opportunistic probes.

Python is the sole producer of repository-family membership and the
root-repository → temporary-repository → resource tree. Reports include exact
states and IDs, ports and domains, root/effective CPU and memory totals,
unclassified or stale processes, crash evidence, cleanup state, and typed log
links. Board and Console render this model without name, path, image, or port
heuristics.

## Current routine caller contract

The immutable `devcoordinator` launcher is the current low-entropy interface to
this authority for routine agent work; `devcoordinator-mcp` exposes the same
contract through MCP `2025-11-25` only. The client derives the canonical current
root or linked temporary worktree and attribution, validates the active release,
authority generation, broker protocol, result schema, and required global
result bound, resolves an exact ID or unique enrolled name, and emits one
bounded decision envelope. No prior MCP, manifest, or caller-override contract
is negotiated alongside it. Deployment rollback may atomically restore the
exact prior release after failed activation, but never keeps prior and current
contracts concurrently exposed.

For governed tests, local attribution is exactly `codex:<thread-id>` or the
`codex:uid:<effective-uid>` fallback and is validated by one shared Python
contract at client production and broker consumption. The distinct normalized
`google:<email>` namespace remains exclusive to the protected Console API
producer. In an all-client local routing profile, current repository generation
outranks tie-breaks; equal-generation duplicates prefer the effective UID and
then the repository owner, while administrative proofs parse their exact UID
entry rather than the merged host view.

Python generates a mutation UUID before discovery or transport and exposes
typed operation, plan, run, and artifact continuations. Runtime desired-state
calls own fresh observation, successful already-desired no-op, safe start/stop
selection, convergence, certainty, and terminal proof. Unknown, unhealthy,
unclassified, or contradictory evidence returns attention without guessing.
Routine test calls compose manifest/prerequisite validation, policy plan
selection, registration, submission, bounded wait/follow, and summary/failure
projection. Handoff and release deliberately stop at an immutable plan until a
separate semantic review submits it.

Targets, status/ensure, operation follow, routine test enqueue, and test follow
each require one caller invocation. Reviewed handoff/release requires one plan
call and one post-review submit call. The six representative source-side output
ceilings total 18 KiB: 3 KiB capabilities, 2 KiB targets, 2 KiB runtime ensure,
3 KiB operation follow, and 4 KiB each for test enqueue and follow. The
efficiency gate's UTF-8 byte-derived token range is explicitly a proxy, never a
provider-native token measurement.

Python owns repeatable execution: repository context and exact target binding,
prerequisite validation, desired-state convergence, policy plan selection,
routine submission/follow, safe retry, and supported durable cleanup,
recovery, replay, or supersession. The agent or user retains semantic goals,
material target/deadline selection, attention remediation, destructive data or
removal work, handoff/release review, and publication. The repository-owned
`software_owned_delivery.py` workflow owns the complete mechanical delivery
cycle after those decisions.

Schema-3 manifests make the safe retry policy explicit per target: one through
four attempts, with only `lease_expired_before_launch` eligible when more than
one attempt is allowed. Test failures, timeouts, and post-launch losses never
become automatic retries through that policy.

## Lifecycle constraints

- Temporary and test work has a positive durable TTL and explicit
  KillAfterRun behavior; cleanup survives caller failure.
- Archive is reversible decommission. Permanent removal is a separate,
  confirmation-bound exact-target cleanup after archive.
- Removal deletes active catalog, policy, allocation, and UI projections while
  retaining tombstones, operations, crash evidence, and logs. An old identity
  cannot return; explicit reinstall creates a new incarnation.
- Cleanup never implicitly deletes remote repositories, credentials, database
  contents, Docker volumes, images, or unrelated resources.
- Installed service roles use one fixed OS-supervised runner under the exact
  enrolled execution UID for cross-account start, stop, and restart. A first
  non-worker start records Keep Alive off unless a policy is explicit. Keep
  Alive workers commit every unexpected exit before restart; ten crashes in an
  inclusive five-minute window trip a non-expiring breaker by default, and
  only an explicit attributed start re-arms it. Definition replacement remains
  worker-role-only. A network service additionally binds one active port to its
  health endpoint: start/restart proves listener PID identity and exact sealed
  cwd, while stop proves both the original process identity and listener absent.
- Unsupported target/action combinations, unclassified active resources,
  unknown listener ownership, stale identity, and incomplete cleanup fail
  closed instead of falling back to direct host commands.

Docker and database-stack replacement remains a broker-owned composite
operation, never an account-store or client-Compose mutation. One deterministic
operation journal binds the old immutable container, sealed single-replica
Compose service, nested backup/recreate/restore operation IDs, new immutable
identity, and terminal result. Rebind retires the old container authority and
publishes the new membership atomically; database replacement preserves the
logical database binding while moving it to the new physical container. A
fresh strongly verified backup must commit before recreation. Restore writes a
private exact completion receipt, so a lost reply is reconciled without another
restore; absent proof stays outcome-uncertain. Session cleanup distinguishes
borrowed resources from the newly created replacement and removes only the
latter after exact terminal absence proof when TTL or KillAfterRun requires it.

## Ephemeral Docker and tests

New short-lived Docker work is admitted only through administrator-sealed
repository templates. The broker commits the exact account, repository,
template, nonce, immutable definition, TTL, quota, lease, and cleanup policy
before Docker create; it creates stopped, records the full immutable ID, and
then starts. Recovery after a lost reply must prove every precommitted label;
attachment of an unrelated existing container is a separate administrator
operation bound to fresh immutable fingerprints. Cleanup intent dominates
recovery, and ephemeral containers stay outside generic lifecycle and route
controls.

The Coordinator also owns repository-scoped test admission and durable session,
group, case, timing, outcome, and aggregate-statistics records. Repository
manifests provide structured argv, while an unprivileged enrolled-user client
runs the subprocess and reports bounded results. The privileged broker never
executes arbitrary repository commands, and Board and Console consume the same
repository-bound test projection.

## Alternatives rejected

Direct package-manager, shell, Docker, or database commands duplicate
classification, leasing, observation, authorization, and cleanup. Post-start
name-derived container claims leave an unattributed-running window.
Repository-local test stores fragment retention and statistics; broker-side
arbitrary command execution violates the typed privilege boundary. Hand-written
JSON for routine actions fragments validation. UI-side grouping and ownership
by names, paths, ports, Compose labels, or image names previously produced
duplicate projects and action scopes that disagreed with presentation. A
stateless wrapper cannot reap work after its caller disappears.

Expanding skill prose with more manual command sequences still makes every
caller rediscover context, transcribe fields, and reason about replay using
model tokens. Agent-authored shell/JSON wrappers drift from schemas and obscure
uncertain mutation. MCP-only excludes ordinary shells and approval tooling, so
it remains an optional adapter rather than the sole interface. A new workflow
service or database would duplicate the broker/test authorities. Moving
semantic, destructive, handoff, or release judgment into Python would erase
necessary review. A current-contract mismatch cannot be bypassed through
another interface; lower-level structured and administrator operations remain
separate current capabilities.

## Security assumptions

This caller contract follows
[security-assumptions.md](../security-assumptions.md). One developer owns the
host, and local Unix accounts are attribution, accounting, and crash domains,
not mutually distrusting tenants. The client therefore derives local
attribution and uses the peer-authenticated broker without an agent-authored
token, signature, or duplicate handshake. It retains the confirmed required
gates: bounded message shape, known immutable repository/resource identity,
generation fencing, path containment, idempotent operation identity, separate
secret transports, and the existing public authorization boundaries. MCP
approval annotations improve caller ergonomics but never replace broker grants
or semantic user/agent review. The review triggers recorded in that file still
apply before remote workers, mutually distrusting tenants, or secret-bearing
ordinary metadata.
