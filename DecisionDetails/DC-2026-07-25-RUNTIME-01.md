# DC-2026-07-25-RUNTIME-01 — Python owns repository-family runtime coordination

## Durable decision

One typed Python request/report boundary owns status, start, stop, restart,
replace, bounded run, and removal for supported services, Docker resources,
local database stacks, and short-lived containers. Ordinary existing-target
actions use schema-derived flags; structured definitions and run commands use a
request file but enter the same validator.

Every request carries the agent, canonical original worktree, explicit linked
temporary worktree or null, immutable resource identity, purpose, TTL, and
KillAfterRun policy. One canonical worktree is one project. Linked temporary
worktrees remain distinct children of their original repository. Ports are
durable assignments, not opportunistic probes.

Python is the sole producer of repository-family membership and the
root-repository → temporary-repository → resource tree. Reports include exact
states and IDs, ports and domains, root/effective CPU and memory totals,
unclassified or stale processes, crash evidence, cleanup state, and typed log
links. Board and Console render this model without name, path, image, or port
heuristics.

## Lifecycle constraints

- Temporary and test work has a positive durable TTL and explicit
  KillAfterRun behavior; cleanup survives caller failure.
- Archive is reversible decommission. Permanent removal is a separate,
  confirmation-bound exact-target cleanup after archive.
- Removal deletes active catalog, policy, allocation, and UI projections while
  retaining tombstones, operations, crash evidence, and logs. An old identity
  cannot return; explicit reinstall creates a new incarnation.
- Cleanup never implicitly deletes remote repositories, credentials, database
  contents, Docker volumes, images, or unrelated resources.
- Keep Alive workers use a fixed OS-supervised runner under the repository
  owner's UID. Every unexpected exit is committed before restart; ten crashes
  in an inclusive five-minute window trip a non-expiring breaker by default,
  and only an explicit attributed start re-arms it.
- Unsupported target/action combinations, unclassified active resources,
  unknown listener ownership, stale identity, and incomplete cleanup fail
  closed instead of falling back to direct host commands.

## Ephemeral Docker and tests

New short-lived Docker work is admitted only through administrator-sealed
repository templates. The broker commits the exact account, repository,
template, nonce, immutable definition, TTL, quota, lease, and cleanup policy
before Docker create; it creates stopped, records the full immutable ID, and
then starts. Recovery after a lost reply must prove every precommitted label;
attachment of an unrelated existing container is a separate administrator
operation bound to fresh immutable fingerprints. Cleanup intent dominates
recovery, and ephemeral containers stay outside generic lifecycle and route
controls.

The Coordinator also owns repository-scoped test admission and durable session,
group, case, timing, outcome, and aggregate-statistics records. Repository
manifests provide structured argv, while an unprivileged enrolled-user client
runs the subprocess and reports bounded results. The privileged broker never
executes arbitrary repository commands, and Board and Console consume the same
repository-bound test projection.

## Alternatives rejected

Direct package-manager, shell, Docker, or database commands duplicate
classification, leasing, observation, authorization, and cleanup. Post-start
name-derived container claims leave an unattributed-running window.
Repository-local test stores fragment retention and statistics; broker-side
arbitrary command execution violates the typed privilege boundary. Hand-written
JSON for routine actions fragments validation. UI-side grouping and ownership
by names, paths, ports, Compose labels, or image names previously produced
duplicate projects and action scopes that disagreed with presentation. A
stateless wrapper cannot reap work after its caller disappears.

tests under `skills/codex-dev-coordinator/scripts/devcoordinator/tests/` cover
normal and optimized Python. Board and Console tests must reject synthesized
